# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static, single-page memorial site for Scout (a dog), served live at inlovingmemoryofscout.com. There is no build step, package manager, linter, or test suite: plain HTML/CSS/vanilla JS (ES5 style, IIFEs, `var`). This directory **is** the nginx document root, so edits on disk are live immediately.

- Server config: the site's nginx rules (root, media autoindex, backend proxies, deny rules, cache header) live in `server/nginx-site.conf`, which every domain's `listen 443` block in `/etc/nginx/sites-available/` includes (currently `inlovingmemoryofscout.com` and `scout.weisslab.dev`). To serve the site on another domain, give it a server block with its `server_name`, certificate and `include /var/www/inlovingmemoryofscout.com/html/server/nginx-site.conf;` — nothing in the page or backends is tied to a domain. After changing any of it: `sudo nginx -t && sudo systemctl reload nginx`. It sends `Cache-Control: no-cache` for HTML/CSS/JS/TXT (the `map` is in `/etc/nginx/conf.d/scout-cache.conf`), so browsers revalidate those on every visit instead of using a stale copy.
- Local preview: `python3 -m http.server` works for the page itself, but Moments will show its error state because it depends on nginx's autoindex HTML (see below).

## Live site vs. leftover files

Only these files make up the live page:
- `index.html` — all markup (hero `#top`, `#dedication` (Memorial), `#memories`, `#moments` (photos, GIFs and videos; once the slideshow), `#gallery` grid, `#messages`, the `#memory-view` reader, lightbox).
- `style.css` — all styling (light-only; Newsreader + Karla from Google Fonts).
- `memorial.js`, `memorial.css`, `memorial-preview.html` — the memorial text markup and its photos (see Memorial text); the last is the preview `/media-admin` shows.
- `script.js` — all behaviour, as IIFEs: scenes + nav, Moments stack + gallery grid + lightbox (`slideshow()`), hero photo name, memorial text, memories, messages form.
- `server/` — the messages backend (Node, no dependencies; runs as systemd unit `scout-messages`). nginx denies `/server/`, dotfiles (incl. `.git`) and the notes files; see `server/README.md`. Restart the unit after editing `server/messages.js`.
- `media/` — one flat folder for every photo and video (no subfolders). `index.html` points at one directly, the hero photo. Its current name is in `media/page_files.txt` (`intro=<file>`; a leftover `catch=` line is unused); the media manager updates it when it's renamed, and when the owner picks another photo in its "Title page photo" dropdown; `script.js` swaps the new name in. The hero photo stays at opacity 0 (`.is-ready` in `style.css`) until `script.js` has checked `page_files.txt`, so the old photo never flashes up first. If you change that `src` in `index.html`, update `page_files.txt` too.
- `server/media.js` — the media manager at `/media-admin` (systemd unit `scout-media`), and the site's one admin sign-in: `/admin/login` (password `ADMIN_PASSWORD` in `/etc/scout-media.env`, or the owner's own from `/admin/password`, kept hashed in `/var/lib/scout-media/password.json`) sets a site-wide `scout_admin` cookie signed with `SESSION_SECRET`, which `server/messages.js` also holds and checks; `/admin` links to every admin page. The owner uploads, renames and deletes files in `media/` from there, so `media/` changes on disk outside git; `media/` is owned by the `scout-media` user.

Not used by `index.html` (artifacts of earlier tooling/iterations — don't edit them expecting site changes):
- `slideshow.html`, `slideshow.js` — older standalone slideshow reading `media/pictures/slideshow/`, which no longer exists.
- `Scout.dc.html`, `support.js`, `image-slot.js`, `.image-slots.state.json`, `.thumbnail` — an exported design-tool ("dc-runtime"/omelette) mockup; `support.js` is generated code.
- `github.md` — sync notes from that design tool; its paths are partly out of date.

## Scenes (fade between sections)

The page doesn't scroll as one document. Each of the six parts (intro, dedication = Memorial, memories, moments, gallery, messages) is wrapped in a `.scene` div in `index.html`. `script.js` adds `.scenes` to `<html>`, which turns every scene into a fixed full-screen layer, with only `.is-active` visible. Wheel, touch swipe, keyboard and nav links fade to the next or previous scene. A scene taller than the screen scrolls inside itself and only fades once it reaches its top or bottom. All scene CSS is scoped under `.scenes`, so without JS the page falls back to normal scrolling. An inline script in `<head>` adds `is-loading` to `<html>`, which keeps the page blank (`html.is-loading body > *`) until the scenes are set up, so that scrolling fallback never flashes before `script.js` (at the end of the body) runs; `scenes()` removes it, and the head script does after 4 s in case `script.js` never runs. When adding a section, wrap it in `<div class="scene" data-anchor="<id>">`; `script.js` also adds a `.scene-dots` dot for it on the right edge, named after its `.sidenav` link. Videos in `#moments` have no `autoplay`. Once a scene is really on screen (right away, or after its transition clip has finished, i.e. when it starts fading in) the scene code adds `.is-shown`; it fires a `scenechange` event on leaving and again on `.is-shown`. The slideshow's timer and the Moments videos/GIF timers only run while their scene is `.is-shown` (and Moments only while on screen); arriving at the slideshow restarts the top photo's time. A scene can carry `data-clip="<gif or video path>"` and `data-clip-ms` to use that clip as a transition (`.scene-clip`: the old scene fades out, the clip fades in centred in a soft-edged oval (circle on phones and narrow or tall screens) at 75% opacity, fades out, then the new scene fades in via an inline transition-delay; input locked until it ends, except that a fresh scroll, tap, click or key press skips it: `skipClip()`) whenever you arrive at it; it's skipped on the first load and with reduced motion. `data-clip-from="<id or data-anchor>"` limits it to when that's the scene before. A clip belongs to the boundary between a scene and the one before it: it plays crossing that boundary either way, and a jump (nav link, dot) plays the one it would have crossed last (`clipAt()` / `playClip()`). Normally these come from `media/transitions.txt` (`<from>><to>=<gif>` lines, e.g. `top>dedication=x.gif`), set by the "Transition" menu on each GIF at `/media-admin` (one GIF per transition; taken ones greyed out; the list of transitions is `TRANSITIONS` in `server/media.js`, so add one there when adding a section). `script.js` reads it into those attributes and times each GIF to one run from its frame delays (`gifRunMs()`); it preloads only the clips on either side of the current scene, one at a time through the global `clipQueue` (`preloadClip()`), as Blobs; each showing gets a fresh `blob:` URL, because every `<img>` of one GIF URL shares one animation clock (the same GIF may be animating in Moments), which would start the transition mid-loop. If a clip isn't downloaded yet when it's needed (a first visit), `playClip()` holds the new scene hidden (inline opacity/visibility) until it is, up to `CLIP_WAIT_MS` (15 s), then plays it; past that the scene just fades in. A GIF set to "Random" at `/media-admin` goes in a pool (`random=<gif>` lines): every boundary without its own GIF gets `data-clip-random`, and `pickClip()` gives it one from the pool (not the clip played last) when it's next to the current scene, so it preloads, and again after it has played. Renaming or deleting a GIF at `/media-admin` carries its transition over (or drops it).

A little Scout runs along the bottom of the screen chasing a frisbee (`scoutRun()` in `script.js`, an inline SVG; `.runner` in `style.css`): his place across goes from just right of the `.sidenav` to just left of the `.scene-dots`, by how far through the page you are, each scene a stretch of the way and scrolling inside a scene moving him along it (`progress()`, updated on `scenechange` and each scene's `scroll`), so arriving at the next scene finds him there already. `.is-running` (legs, bob) while he moves (1.2 s, the `.runner-go` transition); he keeps facing the way he last went (`.is-left` after going back), the frisbee always ahead of him. On the last scene, once he's stopped, `jump()` leaps for the frisbee (`.is-jumping`, `runner-jump` / `runner-catch`, `JUMP_MS`), and from the top of the leap (`CATCH_AT_MS`) it's in his mouth (`.is-caught`, `.disc`); leaving the last scene lets it go (`letGo()`). The bottom `--runway` (64 px) of every scene is padding, and `.runway` fades the page into the paper there (z-index 300), so he never covers content; `#slideshow-stage`'s max-height leaves room for it. z-index 400: under the transition clips, the memory reader and the lightbox; `pointer-events: none`. Reduced motion: no transition or animations.

Media loading: the scenes are all laid out at once, so `loading="lazy"` alone would fetch everything up front. `whenNear(el, fn, within)` runs `fn` once el's scene is the active one or next to it (`within` 1, the default; 0 = only when active), and for a neighbour only after `clipQueue` settles, so transition clips get the connection first. The slideshow (top `STACK_DEPTH` cards near, the rest when on it), gallery, Moments and message photos set their `src` through it. The `#frisbee` fallback video has `preload="none"` (it's 44 MB and Moments replaces it); Moments' cards switch their copies back to `preload="metadata"`.

## Moments (once the slideshow) and the gallery

`script.js` (`slideshow()`) fetches `media/` and parses the **nginx autoindex** HTML listing (`autoindex on` for `location /media/` in `server/nginx-site.conf`) to discover files. Consequences:
- Two plain-text lists in `media/` (one filename per line, edited via the Moments / Gallery checkboxes at `/media-admin`) decide what's used, independently: `not_in_gallery.txt` = files left out of the gallery (default: in it), `slideshow.txt` = files in Moments, photos, GIFs and videos alike (default: not; the name is from when it was the slideshow). A new upload appears in the gallery but not Moments until it's ticked. Moments used to be two sections (a photo slideshow, and Moments for GIFs/videos listed in `moments.txt`); `server/media.js`'s `migrate()` merged `moments.txt` into `slideshow.txt` on start and moved the old transitions, and `script.js` still reads `moments.txt` too if it exists.
- Order: `media/order.txt` (one filename per line, set by dragging rows in the "Display order" view at `/media-admin`) comes first; files it doesn't name follow in natural filename order. With no `order.txt`, it's purely by filename.
- Captions: `media/captions.txt`, `<file>=<caption>` lines, edited per file at `/media-admin`. Shown (as text) under Moments (`#slideshow-caption`) and at the bottom of the lightbox.
- Moments is a stack of cards (`cardStack()`; `.card-stack` / `.stack-card` / `.ss-card` in `style.css`): the top card shows with the next two peeking out below; moving on slides the top card out left (`.is-out`) and tucks it under the bottom while the rest move up. A photo stays on top for `slide_seconds` from `media/settings.txt` (default 5; set in "Moments timing" at `/media-admin`), a GIF for `GIF_PLAYS` (4) runs (its length summed from the file's frame delays in `gifLength()`), a video until it ends (muted, with a `.sound` button; only the top one plays and has controls, only while Moments is `.is-shown` and the lightbox is closed; a lone video loops). The `.ss-progress` bar is a CSS animation for photos/GIFs (`animationend` advances; hovering, the lightbox or another section pauses it) and follows `timeupdate` for a video. A card that fails to load gets `.is-empty` (`.ss-missing`, "Oops") and moves on after 5 s. Card transforms always use the same function list (`transform()` in `cardStack()`) so they interpolate. Headless Chrome barely draws frames, so check the animation there by pausing `getAnimations()`, not by screenshots.
- Dots: with more than 7 (`DOT_WINDOW`), `windowDots()` shows a sliding window of 7 around the current one, the end ones shrunk. Arrow keys move Moments only while it's the section on screen.
- The `#gallery` grid (4 columns, 2 on phones) is built from the same listing, photos and videos (minus `not_in_gallery.txt`), as a masonry layout: 1px grid rows, and `script.js` sets each tile's row span from its picture's shape once it loads. Video tiles show their first frame with a play badge.
- Clicking a photo (in Moments or the grid) opens the lightbox (wheel zoom toward cursor, drag-to-pan, Esc/click-out to close). A gallery video opens in the same lightbox and plays with sound and controls (no zoom).
- If the folder is moved or autoindex is disabled, Moments and the gallery break — update both `DIR` in `script.js` and the nginx `location`.

## Memories

The `#memories` scene (after the Memorial) is a grid of cards from `media/memories.json` (`[{ "title", "text", "photos" }]`, photos a list of files in `media/`, photos, GIFs or videos, up to 30 (`MAX_MEMORY_PHOTOS`), the first the main one; older entries have a single `"photo"` instead, which `readMemories()` in `server/media.js` and `photosOf()` in `script.js` still read), edited in the "Memories" box at `/media-admin` (add, reorder with arrows, delete; "+ Add pictures" opens a grid of photos, GIFs and videos where taps add them in order (numbered) and a second tap takes one off; under each picture ★ makes it the main one, ← → move it, ✕ takes it off; Save sends them all as JSON, action `memories`, which drops duplicates and missing files). Each card is the main picture and title (or the start of the story, with none); a GIF or video as the main picture shows as a still (`still()`: a frame a third of the way in, through `ImageDecoder` for a GIF where the browser has it, else its first frame, on a canvas; a video seeks to a third of its length), with a GIF badge or play badge, and a count badge when there's more than one picture. Tapping a card opens `#memory-view` with its pictures, title and whole story, Previous / Next, arrow keys and swipe; Esc, × or a tap outside closes it, and the scenes ignore input while it's open (`busy()`). With more than one picture they play as a slideshow above the story (`buildPictures()` / `show()`): a photo for `slide_seconds` (`media/settings.txt`, as Moments), a GIF for `GIF_PLAYS` (2) runs, a video until it ends (muted, controls, the shared `soundButton()`), crossfading, with an `.ss-progress` bar, and arrows and dots under it (`.mv-strip`); a swipe on the pictures moves through them instead of the memories; one that fails moves on after 5 s. A single video loops. Stories are paragraphs (blank lines) with `**bold**` / `*italic*` via `memorialInline()` from `memorial.js`, always as text. Renaming a picture at `/media-admin` updates `memories.json`; deleting one takes it out of every memory (`forgetFile`). With no memories the section says they'll be shared soon. The first eight memories were split out of the memorial text on 2026-10-25 (the owner's previous text is in git, commit 5d87cb2).

## Memorial text

The `#dedication` paragraphs come from `media/memorial.txt` (paragraphs separated by blank lines), which the owner edits in the "Memorial text" box at `/media-admin`. It has a little markup: `**bold**`, `*italic*`, a paragraph starting `# ` is a heading, and `(caption[photo.jpg 35% print])` anywhere is a photo or GIF from `media/` with an optional caption, size and frame (`<photo.jpg>` in the brackets works too): on its own between paragraphs it's a `<figure>`; inside a paragraph it's a `<span class="memorial-photo is-inline">` floated from that point, so the rest of the paragraph wraps around it. `memorial.js` (loaded before `script.js`) parses it (`MEMORIAL_TAG`, `memorialPhotos()` = every tag with its position and number `n`, `memorialBlocks()`, `memorialTag()`) and builds DOM nodes, always via `textContent`, never HTML; `MEMORIAL_TAG` in `server/media.js` must match its regex (it rewrites tags when a photo is renamed and drops them when it's deleted, in `forgetFile`).
- Size: % of the text's width (default 46, `MEMORIAL_SIZE`), on phones too but never under 110 px. Photos float beside the text, alternating right and left; from 70% (`MEMORIAL_WIDE`, `.is-wide`) one is centred on its own line and doesn't take a turn; on phones (under 700 px) that's from 50% (`MEMORIAL_WIDE_PHONE`, `.is-wide-phone`).
- Frame: `outline` (default: a thin line offset behind it like the first page's photo, mirrored toward the text), `print` (cream print, slightly tilted), `mat` (a fine line around it) or `none`.
- All photo styling is in `memorial.css` (loaded by `index.html` and the preview). Photos load through `whenNear`, open in the lightbox (`window.scoutLightbox`), and are left out if the file is missing. The first `<p>` (`p:first-of-type`) gets the drop letter.
- The editor: Bold / Italic / Heading buttons; "Add photo or GIF" (thumbnail picker of photos and GIFs, GIFs badged, with caption, size and frame); a sticky photo bar (`#photo-edit`) with Size slider and Frame buttons for the photo whose tag the cursor is in, or that was tapped in the preview (photos are addressed by `n`, their order in the text); "Add photo or GIF" inserts the tag at the cursor (after the word it's in; on the blank line between paragraphs, as its own paragraph); and a live preview that is the real page: `memorial-preview.html` (the site's CSS, `memorial.js`, `html.scenes` and a `.scene`) in an iframe 1280 px (Computer) or 390 px (Phone) wide, scaled to fit, which the admin page fills by calling the frame's `renderMemorial()` (same origin). Keep `memorial-preview.html`'s markup in step with `#dedication` in `index.html`.

`#dedication` is deliberately empty in `index.html` (the owner doesn't want the original text on the site at all, not even as a no-JS fallback); the text only ever comes from `memorial.txt`.

## Messages

The `#messages` scene (below the gallery) has a form for a message and/or up to 10 photos, GIFs and videos (the message is optional when there's a file), and an optional name (blank stays anonymous; shown as "— Name" under the message, and on `/messages-admin` and in the email). Visitors post to `/api/messages` and posts are held as pending. The owner approves them at `/messages-admin` (behind the shared `/admin` sign-in), and only approved messages (and their files, at `/api/messages/file/<id>/<n>`, with Range support for video) are returned to the page. Each file is uploaded on its own first (`/api/messages/upload`, raw body with progress, answered with a token the message then names; nginx allows 310 MB there, the server 8 MB for a photo and 300 MB for a video, by their first bytes). `script.js` shrinks a photo to 2400 px and re-saves it as a JPEG before sending (dropping EXIF/location); GIFs and videos go as they are. Files live in the service's state dir, not the web root. From `/messages-admin` the owner can delete a post, remove one of its files, or "Copy to my media" per file, which hands the file to `server/media.js`'s `/internal/import` (localhost only, shared `IMPORT_TOKEN` in both env files) with the Gallery / Slideshow / Moments ticks and an optional caption. Each new post is emailed to `NOTIFY_EMAIL` (in `/etc/scout-messages.env`) through the server's Postfix (needs the domain's SPF record and reverse DNS; see `server/README.md`). Message text is always rendered with `textContent`, never as HTML. See `server/README.md`.
